# Internationalization (EN)

[🇨🇿 Česky](i18n.md) · 🇬🇧 English

## Principles

- Two locales: `cs` (default, at the root) and `en` (under `/en`). The list lives in `src/i18n/config.ts`.
- **Translated URLs.** The tool's language-independent ID (`TOOL_IDS`: `timer`, `meditation`, `passwords`,
  `invoice`, `compound`) maps to a slug per language in `TOOL_SLUGS`, e.g. `meditation` → `/meditace` (cs), `/en/meditation` (en).
  Always build links with `toolPath(locale, id)` / `homePath(locale)` / `pagePath(locale, id?)`, never by hand.
- **No i18n library, no proxy.** Each language has its own route group with its own root layout (and so its own
  `<html lang>`): `src/app/(cs)/…` and `src/app/(en)/en/…`. All pages are prerendered statically. There is no automatic
  redirect based on `Accept-Language`; the user switches language in the header.
- Both URL sets are real, indexable pages: each page sets `canonical` and `hreflang` alternates
  (`toolMetadata()` / `homeMetadata()`), and `metadataBase` comes from `NEXT_PUBLIC_SITE_URL`.

## Structure

```
src/i18n/
  config.ts        locales, tool IDs, slugs, path helpers
  dictionaries.ts  assembles the dictionaries; the Czech one defines the type
  format.ts        fmt("{n} rounds", { n }) and plural(locale, forms, n)
  provider.tsx     I18nProvider + hooks useLocale / useCommon / useToolMessages
  messages/
    common.{cs,en}.ts    header, theme toggle, footer
    catalog.{cs,en}.ts   launcher card + page intro of every tool
    <tool>.{cs,en}.ts    the tool's UI strings
src/tools/<id>/    client components of the tools (shared by both languages)
src/app/(cs)/…     Czech routes (thin page.tsx files)
src/app/(en)/en/…  English routes (thin page.tsx files)
```

- **Czech is the source of truth.** `xxx.cs.ts` is a plain object; `xxx.en.ts` is typed as `typeof xxxCs`, so a
  missing or extra key in English fails `pnpm typecheck`.
- Dictionaries must stay **serializable** (strings, arrays, objects — no functions), because they are passed from
  the server to client components. Use `{name}` placeholders with `fmt()` and `plural()` for plural forms
  (Czech has `one`/`few`/`other`, English `one`/`other`).
- Client components read texts through `useToolMessages("<id>")`; the `<ToolPage>` wrapper puts only the given
  tool's strings (plus `common`) into the client bundle.
- Pure logic in `src/lib/` contains no user-facing strings — it returns keys/levels and the UI picks the text.
- `localStorage` keys stay language-independent (`tools.<slug>.…`, using the original Czech slug), so settings are
  shared between languages.

## Adding a tool

1. Code in `src/tools/<id>/`, logic in `src/lib/`.
2. `src/i18n/config.ts`: add the ID to `TOOL_IDS` and a slug for each language to `TOOL_SLUGS`.
3. `src/i18n/messages/`: add the card and intro to `catalog.cs.ts` / `catalog.en.ts`, create `<id>.cs.ts` and
   `<id>.en.ts`, then wire them into `dictionaries.ts` (the `cs` and `en` objects).
4. Add the icon to `TOOL_ICONS` in `src/components/home-page.tsx`.
5. Create `src/app/(cs)/<slug>/page.tsx` and `src/app/(en)/en/<slug>/page.tsx`:

   ```tsx
   import { ToolPage, toolMetadata } from "@/components/tool-page";
   import { MyTool } from "@/tools/<id>/my-tool";

   export const metadata = toolMetadata("en", "<id>");

   export default function Page() {
     return (
       <ToolPage locale="en" tool="<id>">
         <MyTool />
       </ToolPage>
     );
   }
   ```
6. Add it to the README tables (both languages), then run `pnpm typecheck` and `pnpm build`.

## Adding a language

1. Add the code to `LOCALES` in `src/i18n/config.ts`, add a slug for it in each `TOOL_SLUGS` entry.
2. Create `*.<lang>.ts` for every message module (typed as the Czech one) and register it in `dictionaries.ts`.
3. Add `src/app/(<lang>)/layout.tsx` (copy the `(en)` one), the `src/app/(<lang>)/<lang>/…` pages, and
   `public/manifest.<lang>.json`.
4. Add the language name to `common.languageNames` in all the dictionaries.
